# 真机向量回放

把**真机会话录下来的上行音频**原速喂回云端，逐轮对比 ASR 与延迟，并审计这一场的**时序与状态轮转**。

```
python bench/replay/run.py --list                       # 看有哪些向量/档案
python bench/replay/run.py --archive <会话名> --turns 3   # 回放前 3 轮
python bench/replay/run.py                              # 用向量库里最新的一份
```

## 默认自己起 harness（不再打生产）

每次回放都**在服务器上起一个只服务本次回放的实例**（默认端口 `8767`，目录 `/tmp/miai-replay`），
档案、记忆、会话指针、播报队列全在它自己目录里：

| 项 | 为什么 |
|---|---|
| 不连生产 `63993` | 以前直连生产，每条连接都会在生产档案目录里生成一份档案，而 `MIAI_ARCHIVE_KEEP` 只留最近 20 个 —— **每回放一场就挤掉一份真实设备档案**（实测 21 个目录里 13 个是回放/bench 场） |
| 隔离 `MEMORY_FILE` | 不然快车道会读到生产的 `MEMORY.md`，同一份向量两次跑结果不一样 |

要连接已有的实例（旧行为）：`--no-spawn --port 63993`。

## 跑完自动审时序与状态

`run.py` 结束时会调用 `scripts/fsm-trace-check.ts` 审这一场的档案，输出逐轮分段与违规：

```
=== 20261117-082058-127.0.0.1_56948  轮次 2  状态事件 6
  #  停嘴→首块  出句→开轮  开轮→首块  中断
   1     2526       624      1316
   2     1569       151      1073  是
  ✓ 没有违规
```

规则（`src/fsm-trace.ts`）：轮次不许嵌套、必须成对；状态转移只走白名单；`closed` 之后不再动；
`tts.first` 必须在 `speaking` 之后且落在本轮；插话必须发 `audio.stop`；一轮不许挂超过 45 s；
停嘴到首块超过 15 s 报违规。老档案没有 `dialog.state` 事件时，状态相关的几条记「缺仪表」跳过 ——
不拿「没记录」冒充「没问题」。

## 为什么是它（而不是 E2E）

真机档案里每场会话都留着：

| 文件 | 内容 |
|---|---|
| `uplink.pcm` | 解码后的 PCM16 16 kHz、**放大前**、从连接建立起连续写 |
| `events.jsonl` | `gate.open` / `gate.close` / `asr.sentence` / `turn.start` / `tts.first` / `turn.end` |

所以「用户说了什么」是**真机真录**的：真实口音、真实噪声、真实停顿、真实打断。
同一份向量可以反复喂 —— 改一次代码跑一次，逐段对比，不受说话人当天状态影响。

E2E（手机喇叭 + 麦克风）只在两种情况下用：没有历史录音、或者要验声学通路本身。
它慢得多、受房间与音量影响，而且素材是合成音。

## 两种回放

| 模式 | 干什么 | 用在哪 |
|---|---|---|
| `--mode utterance`（默认） | 一轮一轮：只放用户说话那一段，等回复念完再放下一轮 | **回归对比**。源档案每轮 ↔ 回放每轮一一对应，①②③ 可以逐条比 |
| `--mode stream` | 整段上行原速重放 | 验打断/旁白这类**跨轮交织**的行为。注意它不可逐轮对账：回复变快之后，原本"用户插话"的那句会变成"干净的新一轮"，轮次结构就变了 |

## 造一段音频，验「一句话被切成两段又并回来」

真机档案里这种片段很少见，所以用 TTS 现造。`client.mjs` 支持直接吃 PCM
（`--pcm a.pcm[,b.pcm]`，每个文件算一轮），所以把几段拼成一个文件就是一轮里的多句：

```bash
# 1) 合成（16 kHz，CosyVoice 直接支持）
#    不想写脚本就复用一个 mjs：cosyVoiceTts({ sampleRate: 16000 }).synthesize('你好呀')
# 2) 裁掉每段自带的 ~600 ms 尾部静音，否则拼出来的间隔比你以为的长得多
# 3) 拼：A + 205 ms 静音 + B
python3 - <<'PY'
sil = lambda ms: b'\x00' * (16000 * 2 * ms // 1000)
open('/tmp/m.pcm','wb').write(open('/tmp/a.pcm','rb').read() + sil(205) + open('/tmp/b.pcm','rb').read())
PY
```

然后**把判停阈值抬上去**，逼出「没说完 → 并下一段」那条分支：

```bash
export SMART_TURN_THRESHOLD=0.99 SMART_TURN_EXTEND_MS=2000
```

默认阈值 0.5 时，干净的 TTS 片段会被判停器各判成一句（实测 0.977 / 0.985），
于是**各自成轮**——这不是 bug，是「用户确实说完了」。要验并段就得让判停说没说完。

跑成功时日志按这个顺序出（`快车道 判停前先问出去` → `预跑作废（判停并了段…）` →
再用并完的文本重新起跑 → 只答一次）。

## 向量库（重要）

回放本身会产生新档案，而服务器 `MIAI_ARCHIVE_KEEP=20` 是滚动删除的。
**踩过**：回放一场 12 轮的真机会话，把它自己挤掉了 —— 工具吃掉了唯一那份输入。

所以第一次用某场档案时，脚本会先 `cp -r` 到 `~/miai-vectors/`，之后**只从向量库读**。
也可以只钉不跑：

```
python bench/replay/run.py --pin --archive <会话名>
```

## 量什么

全部来自**服务端档案**，客户端只负责按原速送音频：

| 段 | 定义 |
|---|---|
| **①** | 停嘴（`gate.close.t − gapMs`）→ `asr.sentence` |
| **②** | `asr.sentence` → `turn.start`（判停决策 + 开轮） |
| **③** | `turn.start` → `tts.first`（dsh + 上游首 token + TTS 首包） |

默认连 `127.0.0.1`（脚本把客户端 scp 到服务器上跑），把公网抖动摘掉；
要比线上真实延迟就 `--host <服务器地址>`。

## 两个照着调过的细节

**起点要往前多带 2 s。** 判停器看的是"最近这一整段波形"；源档案里它手上有会话
开始到当下的全部音频，只给 300 ms 前导会让它判"说完了"的概率偏低 —— 实测第一轮
② 从 150 变成 622（多等一拍）。

**尾巴给 800 ms 静音。** 判停器靠句尾静音判断说完；切在字上它同样会多等一拍。
这段静音落在 `gapMs`（约 2 s）里，不会把下一句带进来。

## 副作用

回放会**真的把这些轮次跑完**，dsh 会话里会多出这些对话。想清干净就删
`~/voice-agent/session.json`（下次连接开新会话）。

## 文件

| 文件 | 作用 |
|---|---|
| `run.py` | 编排：钉向量 → scp 客户端 → 回放 → 取回新档案 → 逐轮对比 |
| `client.mjs` | 线协议客户端（`audioIn: 'pcm16'`），向量回放与单段 PCM 两种模式共用 |

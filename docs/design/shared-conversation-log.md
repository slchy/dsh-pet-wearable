# 设计草稿：单一对话日志（暂不实现）

> 状态：**草稿**。第 4 步只要求「留一页，不做」。
> 相关代码：`src/fronted-agent.ts`（L1 窗口）、`src/session.ts`（L2 会话）、
> 对齐报告见 `docs/fsm-align-report.md`。

## 问题

两条通道各有一份对话历史，靠**拼接**保持一致：

| 方向 | 机制 | 代价 |
|---|---|---|
| L1 → L2 | `pending` 攒最多 4 轮，委派时当 `note` 补进去 | 攒满要强制委派一次；注记不是用户原话 |
| L2 → L1 | 窗口里只留 dsh 最后一句 + 最近 8 条 messages | 更早的 dsh 发言 L1 看不到 |
| L1 → L1 | 自己最近 8 条 messages（≤800 字） | 裁剪后只能委派 |

三套东西合起来能跑，但每次「谁该知道什么」都要现场推一遍，而且**顺序**要靠
`pending` 的时机保证（旁白插进来就可能因果倒置）。

## 目标

一份 append-only 的对话日志：

```
{ seq, at, lane: 'L1' | 'L2', role: 'user' | 'assistant', text, ticket?: {no, gen} }
```

- 两条通道**都写**，写完不可改；`seq` 单调递增
- L1 取最近 N 条做提示词窗口；L2 继续用自己的会话，日志只作对账
- 旁白、后台汇报也进日志（`lane: 'L2'`），带起始 `seq`

## 为什么现在不做

1. **dsh 的会话审计不能拆**：它按完整会话事件落盘，SDK 运行时只暴露
   `session/prompt` / `session/event`，没有「导入一段历史」的接口。要共享就得在
   L2 侧再维护一份，两边一旦不一致更难查。
2. **收益不明确**：窗口 + `pending` 已覆盖实测出现过的场景；真正缺的是「更早的
   dsh 发言」，而那种问题直接委派就好（约 700 ms）。
3. **维护成本**：多一份要落盘、裁剪、迁移的状态，一个人维护不划算。

## 如果以后要做

1. 先加**只读**日志：L1 / L2 都往 `conversation.jsonl` 追加，谁都不改历史。
2. L1 的窗口改成从日志取（语义与现在的 `history` 一致）。
3. 观察一段：日志与 dsh 自己的会话是否一致；不一致先修对账，别急着让 L2 读日志。
4. 最后才考虑让 L2 从日志重建上下文 —— 那一步要 dsh 支持导入历史
   （`session/prompt` 之外还得有 `session/import` 之类），属于上游改动。

## 判定标准（什么时候值得做）

- L1 因为「看不到更早的 dsh 发言」而委派的轮次 > 10%
- 或者出现「旁白与用户话因果倒置」的真机事故

两个条件都不满足时，保持现状。

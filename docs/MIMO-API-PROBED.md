## 1. 结论速览

| | ASR (`mimo-v2.5-asr`) | TTS (`mimo-v2.5-tts`) |
|---|---|---|
| 输入形态 | **整段 base64 内联**（批量） | 纯文本 |
| 输出形态 | SSE 文本 delta | SSE base64 PCM16 |
| 输出是否真流式 | **是**（多增量块） | **是**（多音频块陆续到达） |
| HTTP | 200 `text/event-stream` | 200 `text/event-stream` |

**关键判断：上行批量、下行流式。瓶颈在上行。**

```
上行（ASR）  首字延迟 ≥ 说话时长 + 上传 + ~0.72 s
下行（TTS）  首字延迟 ≈ 0.8 s，且可边生成边播
```

## 2. ASR 实测

### 请求

```json
{
  "model": "mimo-v2.5-asr",
  "messages": [{ "role": "user", "content": [{
      "type": "input_audio",
      "input_audio": { "data": "data:audio/wav;base64,<整段音频>" }
  }]}],
  "asr_options": { "language": "auto" },
  "stream": true
}
```

### 响应结构（SSE，逐行 `data: {...}`）

```json
{"id":"...","choices":[{"delta":{"content":"","role":"assistant","tool_calls":null,"audio_t...}}]}
{"id":"...","choices":[{"delta":{"content":null,"role":null,"tool_calls":null,"audio_tokens...}}]}
{"id":"...","choices":[],"created":...,"model":"mimo-v2.5-asr","object":"chat.comple..."}
[DONE]
```

> 中间那行出现的 `audio_tokens` 字段本次未展开研究，尚未知语义。

### 延迟

| 音频 | 长度 | 首字节 | 首 token | 总耗时 | 增量块 |
|---|---|---|---|---|---|
| `beep.pcm`（纯音调） | 1.60 s | 0.403 s | 0.467 s | 0.562 s | 2 |
| TTS 生成英文（回灌） | 16 s | — | 0.721 s | 1.466 s | 60 |

**判读**

- 16 秒音频用 1.47 秒处理完 ≈ **11× 实时**
- 首 token 远早于总耗时 → 输出确为流式，不是「攒完一次吐」
- 纯音调被识别成「嗯。」—— 无语音输入时模型会给填充词，属正常行为

### 已验证的采样率无关性

同一段 PCM 按 16 kHz 与 24 kHz 分别封成 WAV 喂入，**两者都一字不差识别出原文**。
说明服务端对变速音频有很强鲁棒性（或不采信 WAV 头速率）。

> 副作用：**不能用「喂回去看识别对不对」来判断采样率**。此法已证伪。

## 3. TTS 实测

### 请求

```json
{
  "model": "mimo-v2.5-tts",
  "messages": [
    { "role": "user",      "content": "<风格描述>" },
    { "role": "assistant", "content": "<要朗读的文本>" }
  ],
  "audio": { "format": "pcm16", "voice": "Chloe" },
  "stream": true
}
```

**风格由 user message 承载** —— 同一引擎 + 不同 prompt = 不同语气。
`ADR-004` 的自适应语速可以直接落成风格 prompt，不必维护多套引擎。

### 响应结构

- 音频字段路径：**`choices[0].delta.audio.data`**（base64 编码的 PCM16）
- 首个音频块固定 **7680 字节**（= 3840 samples）
- 结束标记：`finish_reason: "stop"`，`matched_stop: 151645`
- 末行 `usage`：`completion_tokens` / `prompt_tokens`

### 延迟

| 文本 | 音频块 | PCM 字节 | 首字节 | 首音频块 | 总耗时 |
|---|---|---|---|---|---|
| 英文 230 字符（快语速风格） | 50 | 768 000 | 0.686 s | 0.772 s | 3.817 s |
| 中文 28 字 | 16 | 253 440 | 0.750 s | 0.883 s | 1.764 s |

**判读**

- 首音频块 0.77–0.88 s 且远早于总耗时 → **真流式，可边生成边播**
- 这是下行体验的关键指标：只要 ASR 那边能及时给出文本，TTS 首字延迟可以压在 1 秒内

## 5. TTS 采样率：**24 kHz**（已确认）

`audio.format = "pcm16"` 只定**编码**，不定**速率**。若服务端是 24 kHz 而按 16 kHz 播，
声音会变成 1.5 倍速并升调；反之变慢变低。

### 结论

> **24 kHz，单声道，PCM16 小端。**
> 确认方式：人听对比 `tmp\tts24.wav`（16.00 s）与 `tmp\tts16.wav`（24.00 s），
> 前者语速与音高正常。

### 两种自动探测为何都失败（留存以防后人重踩）

**尝试一：回灌 ASR —— 证伪**

按 16 kHz / 24 kHz 分别封装后喂回 ASR，**两者都完整识别出原文**。
服务端对变速音频有很强鲁棒性，此法无判别力。

**尝试二：高频能量 —— 无判别力**

按 24 kHz 解释，测 8.5–11.5 kHz 带通：`mean −34.8 dB / max −6.0 dB`，有能量。

但两种假设下这个频段都会有信号：

- 若真是 24 kHz → 是真实齿音
- 若是 16 kHz 被当 24 kHz → 原本 5.7–7.7 kHz 的成分被拉伸到此处

### 当时剩下的推断（事后看全部指对了，但不应当作方法论）

- 中文 28 字按 24 kHz = 5.28 s（≈5.3 字/秒）；按 16 kHz = 7.92 s（≈3.5 字/秒，偏慢）
- 英文 230 字符按 24 kHz = 16.00 s；按 16 kHz = 24.00 s（用户给的风格是 "Fast pace"）
- 首音频块固定 7680 字节：24 kHz 下是 160 ms，16 kHz 下是 240 ms

### 对播放端的影响

现有 `MainPlay` 写死 `SAMPLE_RATE = 16000`。**直接拿 24 kHz 的 PCM 用 16 kHz 播 = 1.5 倍速升调。**

两个选择：

| 方案 | 做法 | 代价 |
|---|---|---|
| A（推荐） | `AudioTrack` 直接设 24 kHz | 系统负责向 A2DP 重采样，我们不做任何转换 |
| B | 先把 24 kHz 降到 16 kHz | 我们自己引入一次重采样，多一层失真源 |

上行的 mSBC 仍是 16 kHz，上下行采样率**不相等**，不要误用同一个常量。

## 6. 对架构的影响

### 已确定

1. **下行可以做到「边生成边播」** —— 首音频块 0.8 s，音频块陆续到达
2. **上行做不到「边说边识别」** —— 必须整段就绪才能发
3. `pcm16` 输出与现有 `AudioTrack` 推送链路格式一致（采样率另说）

### 待定

1. 是否存在独立的流式音频输入接口 —— **决定能不能做真 realtime**
2. TTS 采样率 —— 决定播放端要不要重采样

### 端到端延迟估算（基于实测，非猜测）

```
用户说完最后一个字
   ↓  base64 编码 + 上传（4.8 s 音频 ≈ 128 KB，WiFi 下 < 100 ms）
   ↓  ASR 首 token                     0.72 s
   ↓  agent 首 token                   待测（ADR-003）
   ↓  TTS 首音频块                     0.80 s
   ↓  下行传输 + AudioTrack 起播        待测
= 约 1.6 s + agent 时间（从"说完"起算）
```

对比当前冒烟链路（批处理 + adb pull/push + 45 秒窗口），这是数量级的改善 —— 
但仍**不是**「边说边出字」。

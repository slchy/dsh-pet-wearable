## 一、目标与口径

### 1.1 用户能感知的量

| 指标 | 定义 | 怎么算 |
|:---|:---|:---|
| **首声延迟** | 停嘴 → 设备收到首块音频 | ①停嘴→定稿 + ②定稿→开轮 + ③开轮→首块。**按逐轮合计排序取 p50/p90**，快车道与委派**分开**；委派轮再分「到回执」和「到答案」 |
| **慢轮次占比** | 首声 > 1500 ms 的轮次比例 | 同上，数比例。**这是「稳」的指标，比 p90 更不容易被单点污染** |
| **可感知误切** | 用户没说完、系统已经出声，**用户能察觉到** | 两类：**B 出声后被打断**（`turn.end.interrupted`）、**C 半句被当整句回答**。见下方说明 |
| **答偏** | 因文本不完整而答错 | 见 1.4 —— **目前只能人工抽样**，不要假装有自动指标 |
| **多余轮次** | 不是用户完整意图触发的轮次 | 误识别（`Yeah.` / `Thank you.`）、被切开的开头语单独成轮 |

> **「出声前被吸收的停顿」不算可感知误切。** 前后半句合成一轮、前半句没有下行音频
> —— 用户听到的是一句完整的话，没有任何可察觉的异常。它单独作为一个**验收项**
> （「0.5–0.8 s 的停顿能不能合并成一轮」），不计入误切率。把它算成误切会让这个
> 指标失去意义：合并成功本来是**想要的结果**。

### 1.3 四条口径规则（写死，不许各写各的）

1. **三段相加必须等于合计。** 逐轮算 `①+②+③` 再取中位，**不是各段中位相加**。
   这两者的差别在两头分布时能到 140 ms。
2. **缺数据记 `null`，不拿 0 冒充。** 仪表没落、配对失败、`①<0`（`gate.close`
   配到了上一段语音）都记 `null` 并从该指标的分母里剔除，**不是当 0 算进去**。
3. **坏样本自动剔除，不靠人眼。** `①<0` 已经是脚本行为（`badSample`，分组表显示
   「可算/总轮（坏样本 N）」）。
4. **脚本和线上用同一套判定规则。** 分析脚本里的「命中 / 合并 / 打断」必须与
   `dialog-fsm` 的判断同源；不一致时以代码为准，改脚本。

### 1.4 现在测不出来的两项（要承认）

| 指标 | 可自动测 | 说明 |
|:---|:---:|:---|
| 首声延迟、慢轮占比 | ✅ | 档案三段 |
| 「被吸收的停顿」 | ✅ | 前后半句合成一轮、前半句无下行音频 |
| 误切 B（出声后被打断） | ✅ | `turn.end.interrupted` |
| **误切 C（半句被当整句答）** | ❌ | 需要「用户本来还想说什么」这个 ground truth |
| **答偏** | ❌ | 需要标准答案 |

两条路：**人工抽样标注**，或用弱代理。

弱代理的形态是：**下一轮的定稿把上一轮那句接着说完**（上一轮是前缀，下一轮是余下
部分）。它在「开头语被切开」这一类上成立 —— `20261119-160921` 的「你说。」→
«Yeah.» → 「你说我要不要先去睡一会儿？」就是这种形态。但它**没有被验证过**：既没
量过误报（正常的两句也有前后接续关系），也没量过漏报。在验证之前，**不要把它的
命中数当成误切 C 的次数**。

**任何报告里这两项为空，是在等标注，不是在说「0 次」。**

|:---|:---:|:---:|:---:|:---:|

### 2.3 多余轮次与实际观察到的误切

| 类别 | 数量 | 出处 |
|:---|:---:|:---|
| 疑似误识别（纯英文 / 单字成句） | **6 / 112**（5.4%） | 四场合计：`好。` `是。` `Okay.` `Yeah.` `明。` `嗯。` |
| 开头语单独成轮（可能被切开的半句） | **7 / 112**（6.2%） | `对了。` `说真的。` `我觉得吧。` `我跟你说。` `那个。` `你说。` `你觉得。` |
| 可感知误切 B（出声后被打断） | **7 / 112**（6.3%） | `turn.end.interrupted`：15:37 场 4、16:00 场 1、16:09 场 2、03:15 场 0 |
| **「出声前被吸收的停顿」（合并成功）** | **0 例已验收** | 两处候选（`20261119-160921` 的「你说。」→«Yeah.»、`20261119-153754` 的停顿对）**回看都是两轮独立、前半句有出声**，不算合并 |

**结论**：合并这条路径**还没有一例被验收过**。验收需要 0.5–0.8 s 的停顿样本，
而人为停顿两次都超过 1 秒 —— 所以要用**合成停顿**（切出前后半句、中间插指定长度
底噪）来验，而不是再录一场。

### 2.4 TTS 首包长尾（决定 p90 的那一项）

| 统计 | 值 | 出处 |
|:---|:---|:---|
| 首包 > 900 ms 的轮次 | **8 / 112**（7.1%） | 四场合计；每次 1.3–4.5 s |
| 这些轮次的共同点 | **全部是 `prefetch` 认领轮**（`spec` 轮最高 648 ms） | `2026-11-20` 核对 |
| 文本送达 | 全部在 `finish-task` 前送完（首批→末批 0–123 ms） | `tts.done` |
| 主线程 | `loop_max_ms` 全场 ≤7 ms | `turn.end` |
| 厂商侧 | 探针 140 次（`base` 60 + `live` 80）**0 次 >1000 ms** | `probe-cosyvoice-feed.mjs` |
| 「收尾→首块」（纯服务端） | 正常轮中位 326；两个长尾轮 1250 / 1339 | `tts.done` + `tts.first` |

剩下的可能只有一个：**真机 + 认领**这个交叉点。回放里 7 个认领轮全部正常
（303–495 ms），所以复现不了。→ §7.3 待定 1。

## 三、原则（六条，每条附来由）

1. **出声之前一切可撤销，只有放出声音才是决定。**
   来由：链路延迟本身就是保护窗口 —— **如果**用户在出声前把话接上，这次回复应当
   作废、两句合并成一轮。⚠️ **这条保护窗口「有多宽」尚未验收**：已经观察到的是
   「超过 1 秒的停顿保不住」，0.5–0.8 s 这一段**一个样本都没有**（见 2.3）。
   在合成停顿实验做完之前，这条只能当设计意图，不能当结论引用。

2. **刹车用可观测的事实，不用弱预测。**
   来由：`looksUnfinished()` 与语气词放行都是手写词表。2026-11-19 的两批手工标注上，
   前者命中 **0/3**、后者命中 **0/8** —— 在这批数据里它们一次都没起作用。弱预测只能
   放在**不花钱的位置**（与别的环节并行），或者**带上限**。

3. **所有等待受同一个上限约束，任何路径不得绕过。**
   来由：`TURN_JUDGE_MAX_OPEN_SILENCE_MS` 就是为这个加的 —— 加之前有分支能
   绕过它一直等。

4. **等待只有被别的串行环节遮住时才免费。**
   来由：判停的 400 ms 原本藏在模型段（300–570 ms）后面；模型段回到 184 ms
   之后，这 400 ms 变成纯成本。**同一条配置的代价会随上游变快而变化** ——
   数字要跟着被遮住的那个环节一起重算。

5. **投机不能改变正确性。**
   来由：投机认领从「覆盖 ≥60%」收紧成「**去全部标点后完全一致**」。宽松的
   判据省的那点时间，远小于答偏一次的代价。

6. **同步上下文和回答用户是两件事。**
   来由：`FAST_LANE_KEEP_TURNS` 曾经让「攒满 4 轮就整句交给 dsh」，于是每 4 轮
   就有 1 轮（用户只是想聊两句）要等 6–8 秒。dsh 需要看到对话 ≠ 用户需要等 dsh。

> 新策略先对照这六条。违反了要写清理由，**而不是不写**。

## 五、改动流程：五个问题

动手前在提交信息或 PR 里回答完：

| 问题 | 不合格的答法 |
|:---|:---|
| **动的是哪个指标、哪一批轮次？** | 「让延迟更低」 |
| **预期收益多少？算式写出来。** | 「应该能省几十毫秒」 |
| **会不会影响正确性？** | 空着不写（等于没说） |
| **怎么验证？探针 / 回放 / 真机，为什么选它？** | 「跑一场看看」 |
| **怎么回退？旋钮是什么？** | 「改回来就行」（没说改哪个） |

两条纪律：

- **一场验收只验一个改动。** 攒在一起就分不清是谁的功劳。
- **新机制先讨论再做。** 自动化 / 自愈 / 监控尤其 —— 代码越多维护量越大。

## 六、测量方法：把踩过的坑写成检查项

这一节是这份文档里最实用的部分。**2026-11-18 至 11-20 的弯路，大部分出在这里，不是出在代码里。**

| 检查项 | 踩过的具体形态 |
|:---|:---|
| **选择偏差** | 只看「等到放行」的 5 个长等待轮次，得出「0 次用户接着说」——而用户如果在等待期间说话了，那次等待就不会以放行结束，根本不会出现在这 5 轮里 |
| **中位数** | 各段中位相加 ≠ 合计的中位（差 140 ms）。②是两头分布（七成近 0、三成 ~474），中位 8 ms 会掩盖平均值 130 ms |
| **归因** | 只影响少数轮次的改动，要先说明它们**是否跨过了中位**，再谈对 p50 的作用。4 轮从中位之上移到之下让 p50 跳了 127 ms，换个分布更平滑的样本只值几十毫秒 |
| **样本量** | 写明 n 和**能分辨的最小差别**。小于它不下结论。8 轮里投机最多覆盖两三轮到不了中位 |
| **回放 ≠ 真机** | 已确认的三处差异：包节奏（回放 20 ms、真机 75 ms）、轮次间隔（回放常是热的，真机 5–7 s）、连接冷热。**回放能证明「走哪条腿」，不能证明绝对延迟** |
| **基准对应线上的哪个工作点** | 引用任何探针数字前先写清它对应线上哪一版配置。`base` 探针 316 ms 对应「整句一次送完」，而线上是「首 1 字 + 50 ms」= 380 |
| **观测优于猜** | 优先取可复算的证据（`uplink.pcm` 可重算任意增益、`loop_max_ms` 可判主线程卡顿），不针对着代码猜 |
| **改动前后要能对比** | 所以仪表缺了记 `null`，不拿 0 冒充 |

### 6.1 每种验证手段能证明什么

| 手段 | 能证明 | 不能证明 |
|:---|:---|:---|
| **探针**（`bench/latency/`） | 单个外部依赖的分布与边界（厂商长尾、门槛、超时） | 我们自己的链路 |
| **真机回放** | 走哪条腿、合并/打断路径、状态轮转 | 绝对延迟（间隔是热的）、需要真机负载才出现的偶发 |
| **真机录音** | 一切 | 单场绝对值不可比（台词不同），只做**前后配对** |
| **离线统计**（`silence-runs.py` / `partial-timeline.py`） | 分布与门槛的敏感性 | 真实因果 |

### 6.2 自动化测试基线（四层）

延迟**不能靠单元测试断言**——它依赖外部服务、网络和设备。所以分成四层，各回答一个
不同的问题、各在不同的成本上。

| 层 | 回答什么 | 需要什么 | 频率 | 红了意味着 |
|:---|:---|:---|:---|:---|
| **L1 不变量** | 改 A 会不会静默破坏 B | 源码 | 每次 commit（毫秒） | 参数关系不自洽 |
| **L2 口径基线** | 量出来的数字定义变了没 | 合成档案 | 每次 commit（毫秒） | 分析算法改了 |
| **L3 回放基线** | 我们的链路变慢/变快了没 | 服务器 + 固定向量 | 每批改动（~5 分钟） | 逻辑回归（**不是**性能回归） |
| **L4 探针基线** | 厂商侧漂了没 | 网络 + key | 手动/夜间 | 外部依赖变化 |

**每条命令、每个容差是怎么来的、判什么不判什么，都在
[`TOOLS.md`](./TOOLS.md) §3.1「延迟回归的四层闸门」。** 这里只留三条最容易被忘掉的：

1. **L3 的容差是量出来的，不是设计的。** 第一版按「单次内 MAD 的 2–3 倍」定容差，
   2026-11-20 真机回放一跑红 **61 处**；改成实测跨次噪声底（同一份代码
   `--repeat 3`）才稳定。**① 逐轮抖动 280 ms，所以它不设判据**；③ p50 只抖 46 ms，
   所以它设。
2. **L3 只判汇总，逐轮一律只打印。** 单轮方差大于系统性变化。
3. **回放本身必须先可信。** 2026-11-20 出现过「17 轮只跑出 4 轮」，查明是回放客户端
   的假打断（下一句在下行停止 1.5 s 就推进，而服务端此时仍在 `speaking`）。修后连跑
   两次通过。比对器把「轮数塌了」单独报一条，因为**它既可能是真回归，也可能是回放
   又抖了**。

**做不到自动化的事（不是缺陷，是边界）**

| 想自动化 | 为什么不能 |
|:---|:---|
| 真机绝对 p50 | 台词不同不可比；需要人戴设备 |
| TTS 那 7%（8/112）的 1–4 s 长尾 | 需 n ≈ 100+ 才稳定复现，十几轮回放看不到 |
| 真实间隔下的连接冷热 | 回放造不出 5–7 s 的空闲 |
| 误切 C / 答偏 | 没有 ground truth（见 1.4） |

**L3 的定位是「逻辑回归闸门」，不是「性能验收」。** 性能验收仍然只有真机录音。

### 7.2.1 实验无效 —— **不要当成已经证伪**

这两次实验的数据不足以支持任何结论。以后重开时不用背「已经试过不行」这个包袱：

| 实验 | 实际发生了什么 | 为什么算无效 |
|:---|:---|:---|
| 「partial 一到就发」（2026-11-19） | 三次真机测下来差别在**投机覆盖率**、不在触发时机；顺带暴露两个 bug（已修） | 覆盖率的差别掩盖了触发时机，**没有对照出「一到就发」本身的效果** |
| 「说话中变长重来」（2026-11-19，`830768d`） | 在「完全一致」门槛下它永远认不回来（沿用的是前缀不是全文）→ 已改成「变长就重发」 | 那次测的是**坏掉的实现**，不是这个策略 |

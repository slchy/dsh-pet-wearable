## 一、目标和口径

### 1.1 五个用户能感知的量

| 指标 | 定义 | 怎么算 |
|:---|:---|:---|
| **首声延迟** | 停嘴 → 设备收到首块音频 | ①停嘴→定稿 + ②定稿→开轮 + ③开轮→首块。**按逐轮合计排序取 p50/p90**，快车道与委派分开；委派轮再分「到回执」和「到答案」 |
| **慢轮次占比** | 首声 > 1500 ms 的轮次比例 | 同上，数比例。**这是「稳」的指标，比 p90 更不容易被单点污染** |
| **可感知误切** | 用户没说完而系统已经出声 | 三类分开：A 出声前被吸收（合并成一轮）、B 出声后被打断、C 半句被当整句回答 |
| **答偏** | 因文本不完整而答错 | 见 1.3 —— **目前只能人工抽样**，不要假装有自动指标 |
| **多余轮次** | 不是用户完整意图触发的轮次 | 误识别（`Yeah.` / `Thank you.`）、被切开的半句 |

### 1.2 四条口径规则（写死，不许各写各的）

1. **三段相加必须等于合计。** 逐轮算 `①+②+③` 再取中位，**不是各段中位相加**。
   这两者的差别在两头分布时能到 140 ms。
2. **缺数据记 `null`，不拿 0 冒充。** 仪表没落、配对失败、`①<0`（`gate.close`
   配到了上一段语音）都记 `null` 并从该指标的分母里剔除，**不是当 0 算进去**。
3. **坏样本自动剔除，不靠人眼。** 上面那条 `①<0` 已经是脚本行为；同类的
   「`①` 大于整轮」也要能自动识别，不要让分析者每次手工排除。
4. **脚本和线上用同一套判定规则。** 分析脚本里的「命中 / 合并 / 打断」必须与
   `dialog-fsm` 的判断同源；不一致时以代码为准，改脚本。

### 1.3 现在测不出来的两项（要承认）

| 指标 | 可自动测 | 说明 |
|:---|:---:|:---|
| 首声延迟、慢轮占比 | ✅ | 档案三段 |
| 误切 A（出声前被吸收） | ✅ | 前后半句合成一轮、前半句无下行音频 |
| 误切 B（出声后被打断） | ✅ | `turn.end.interrupted` |
| **误切 C（半句被当整句答）** | ❌ | 需要「用户本来还想说什么」这个 ground truth |
| **答偏** | ❌ | 需要标准答案 |

后两项只有两条路：**人工抽样标注**，或用弱代理（「下一轮定稿是上一轮的后缀」
—— 实测 8 个停顿句里 6 个是这种形态，代理勉强可用）。**任何报告里这两项为空，
是在等标注，不是在说「0 次」**。

## 二、原则（六条，每条附来由）

1. **出声之前一切可撤销，只有放出声音才是决定。**
   来由：链路延迟本身就是保护窗口 —— 停嘴后 850 ms 内接上仍落在出声前，
   会合并。所以「等一会儿」不全是浪费，但**要算清等的是保护还是空转**。

2. **刹车用可观测的事实，不用弱预测。**
   来由：`looksUnfinished()` 那张词表、语气词放行表，都是弱预测。删掉之后
   判停的误判率没有变差。弱预测只能放在**不花钱的位置**（与别的环节并行），
   或者**带上限**。

3. **所有等待受同一个上限约束，任何路径不得绕过。**
   来由：`TURN_JUDGE_MAX_OPEN_SILENCE_MS` 就是为这个加的 —— 加之前有分支能
   绕过它一直等。

4. **等待只有被别的串行环节遮住时才免费。**
   来由：判停的 400 ms 原本藏在模型段（300–570 ms）后面；模型段回到 184 ms
   之后，这 400 ms 变成纯成本。**同一条配置的代价会随上游变快而变化** ——
   数字要跟着被遮住的那个环节一起重算。

5. **投机不能改变正确性。**
   来由：投机认领从「覆盖 ≥60%」收紧成「**去全部标点后完全一致**」。宽松的
   判据省的那点时间，远小于答偏一次的代价。

6. **同步上下文和回答用户是两件事。**
   来由：`FAST_LANE_KEEP_TURNS` 曾经让「攒满 4 轮就整句交给 dsh」，于是每 4 轮
   就有 1 轮（用户只是想聊两句）要等 6–8 秒。dsh 需要看到对话 ≠ 用户需要等 dsh。

> 新策略先对照这六条。违反了要写清理由，**而不是不写**。

## 四、改动流程：五个问题

动手前在提交信息或 PR 里回答完：

| 问题 | 不合格的答法 |
|:---|:---|
| **动的是哪个指标、哪一批轮次？** | 「让延迟更低」 |
| **预期收益多少？算式写出来。** | 「应该能省几十毫秒」 |
| **会不会影响正确性？** | 空着不写（等于没说） |
| **怎么验证？探针 / 回放 / 真机，为什么选它？** | 「跑一场看看」 |
| **怎么回退？旋钮是什么？** | 「改回来就行」（没说改哪个） |

两条纪律：

- **一场验收只验一个改动。** 攒在一起就分不清是谁的功劳。
- **新机制先讨论再做。** 自动化 / 自愈 / 监控尤其 —— 代码越多维护量越大。

## 五、测量方法：把踩过的坑写成检查项

这一节是这份文档里最实用的部分。**这几天大部分弯路都出在这里，不是出在代码里。**

| 检查项 | 踩过的具体形态 |
|:---|:---|
| **选择偏差** | 只看「等到放行」的 5 个长等待轮次，得出「0 次用户接着说」——而用户如果在等待期间说话了，那次等待就不会以放行结束，根本不会出现在这 5 轮里 |
| **中位数** | 各段中位相加 ≠ 合计的中位（差 140 ms）。②是两头分布（七成近 0、三成 ~474），中位 8 ms 会掩盖平均值 130 ms |
| **归因** | 只影响少数轮次的改动，要先说明它们**是否跨过了中位**，再谈对 p50 的作用。4 轮从中位之上移到之下让 p50 跳了 127 ms，换个分布更平滑的样本只值几十毫秒 |
| **样本量** | 写明 n 和**能分辨的最小差别**。小于它不下结论。8 轮里投机最多覆盖两三轮到不了中位 |
| **回放 ≠ 真机** | 已确认的三处差异：包节奏（回放 20 ms、真机 75 ms）、轮次间隔（回放常是热的，真机 5–7 s）、连接冷热。**回放能证明「走哪条腿」，不能证明绝对延迟** |
| **基准对应线上的哪个工作点** | 引用任何探针数字前先写清它对应线上哪一版配置。`base` 探针 316 ms 对应「整句一次送完」，而线上是「首 1 字 + 50 ms」= 380 |
| **观测优于猜** | 优先取可复算的证据（`uplink.pcm` 可重算任意增益、`loop_max_ms` 可判主线程卡顿），不针对着代码猜 |
| **改动前后要能对比** | 所以仪表缺了记 `null`，不拿 0 冒充 |

### 5.1 每种验证手段能证明什么

| 手段 | 能证明 | 不能证明 |
|:---|:---|:---|
| **探针**（`bench/latency/`） | 单个外部依赖的分布与边界（厂商长尾、门槛、超时） | 我们自己的链路 |
| **真机回放** | 走哪条腿、合并/打断路径、状态轮转 | 绝对延迟（间隔是热的）、需要真机负载才出现的偶发 |
| **真机录音** | 一切 | 单场绝对值不可比（台词不同），只做**前后配对** |
| **离线统计**（`silence-runs.py` / `partial-timeline.py`） | 分布与门槛的敏感性 | 真实因果 |

### 5.2 自动化测试基线（四层）

延迟**不能靠单元测试断言**——它依赖外部服务、网络和设备。所以分成四层，各回答一个
不同的问题、各在不同的成本上。**只有前两层能进 `npm test`。**

| 层 | 回答什么 | 需要什么 | 频率 | 红了意味着 |
|:---|:---|:---|:---|:---|
| **L1 不变量** | 改 A 会不会静默破坏 B | 源码 | 每次 commit（毫秒） | 参数关系不自洽 |
| **L2 口径基线** | 量出来的数字定义变了没 | 合成档案 | 每次 commit（毫秒） | 分析算法改了 |
| **L3 回放基线** | 我们的链路变慢/变快了没 | 服务器 + 固定向量 | 每批改动（~3 分钟） | 逻辑回归 |
| **L4 探针基线** | 厂商侧漂了没 | 网络 + key | 手动/夜间 | 外部依赖变化 |

**L1 — 跨参数不变量**（`scripts/time-knobs.py --check`，`tests/qos-invariants.test.ts`）

每个模块的单测只守自己。L1 守两个模块之间的关系，这类改动**没有任何单测会红**：

| 关系 | 违反后的后果 |
|:---|:---|
| `VOICE_COMMIT_MS` ≤ `VOICE_SPECULATE_MS` ≤ `VOICE_PAUSE_DETECT_MS` | 投机跑到封段前面，拿未定稿的中间结果认领，静默失效 |
| `TURN_JUDGE_WAIT_BUDGET_MS` ≥ `TURN_JUDGE_EXTEND_MS` | 预算比一拍还短，等于没有预算 |
| `TURN_JUDGE_MAX_OPEN_SILENCE_MS` ≥ `VOICE_OPEN_QUIET_MS`（及 `_SHORT`） | 开轮门槛永远够不着，只能撞上限 |
| `PREWARM_TTL_MS` > `TURN_JUDGE_SEQUENCE_BUDGET_MS` | 序列句等满预算时预热 task 已过期，付一次冷启动 |
| `MIAI_HTTP_KEEPALIVE_MS` < 服务端空闲超时（60 s） | 复用到已关的连接，那一次请求**直接失败** |

数值**从源码扫**，不是文档里抄的；`tests/qos-invariants.test.ts` 里还有一条元测试
（注入一个必然违反的关系，确认检查器会红），防止它变成永远绿的摆设。

> 已存在一条警告：`MIAI_HTTP_KEEPALIVE_MS=50 s` 超过 `fetch` 实测验证过的 45 s
> （60 s 是 `https.Agent` 的结果）。真机最大轮间隔 16.7 s 从未触及，所以是警告不是失败。

**L2 — 口径基线**（`tests/latency-report-golden.test.ts`）

一份**合成**档案（无真实地址、无录音）→ 逐轮分段 + 三张分组表的数字全部钉死。
守的是测量本身：各段中位相加、① 算成负数、中位掩盖两头分布 —— 这些都不会让任何
功能测试变红，只会让报告里的数字悄悄变成另一个东西。

还有一组**边界值**轮次（①=0、②=70、合计=2000、只缺 `turn.end`），是变异测试逼出来的：
第一版的所有样本都远离判据（①只有 −317、②只有 0/450、合计只有 ≤1050 或 8300），
于是四个判据改成相邻值都能通过。

**测试本身有效吗：`npm run mutate`**（`scripts/mutation-check.py`）

`tests/latency-report-golden.test.ts` 断言了一组数字，但「数字对得上」不等于
「测试有效」—— 换一种算法也可能算出同一个数。定向变异就是查这个：12 个变异体，
每个对着一条真实口径规则，**要求 11/11 全杀 + 1 个对照组存活**。

第一次跑是 **7/12**。存活的五个全是真问题：四个判据因为样本远离边界而放过，
第五个暴露得更深——`usable` 过滤器原本写成「`firstWordMs` 有值 **且** `missing` 为空」，
把「只缺 `turn.end`」的轮次也剔出了分母，而 `turn.end` 只影响「有没有被打断」，
**不影响首字延迟**，剔掉是白丢样本。已改成只按「能不能算出首字」筛。

> **变异检查不能进 `npm test`**：它会改写 `src/` 再跑测试，和并行执行直接冲突
> （第一次接进来就撞了）。所以是独立命令；`npm test` 里只留一条不碰源码的守卫
> （`--verify`：每个变异体的匹配点必须还在），防止改判据后清单静默过期。


**L3 — 回放基线**（`bench/replay/run.py --baseline`，基线在 `bench/replay/baseline/`）

```
固定向量 → --baseline-save 在已知良好 commit 上生成 → 之后 --baseline 比对
```

**比的是回放 vs 回放，不是回放 vs 真机。** 同一份向量：回放 ③ = 648，真机当时 = 543
—— 回放**更慢**。差的 ~300 ms 主要在 TTS `setup`（回放 348 常数、真机 54 常数）：
回放轮与轮之间没有间隔，预热 task 的 `run-task` 正好落在上一轮还在合成的时候，排队。
两边各自是常数，所以只能同环境对同环境。

判什么：

| 字段 | 判 | 容差 | 理由 |
|:---|:---:|:---:|:---|
| `①`（停嘴→定稿） | ✅ 逐轮 | ±80 ms | 同一份音频 + 同一 ASR，封段时刻应稳定 |
| `②`（定稿→开轮） | ✅ 逐轮 | ±60 ms | 同一句上判停给的分几乎不变 |
| ASR 文本 | ✅ 严格相等 | 0 | 同一音频，文本一变就是配置或归一化改了 |
| `path`（fast / dsh） | ✅ 严格相等 | 0 | 走哪条腿不该漂 |
| `batches`（送批次数） | ✅ 严格相等 | 0 | 纯逻辑 |
| `first_text` / `last_text` | ✅ 逐轮 | ±60 ms | **回放里有效**：只取决于我们怎么把字送给 TTS |
| `③`（开轮→首块） | ❌ 只记录 | — | 含厂商合成长尾（>900 ms 占一成），判它等于抛硬币 |

**容差来自哪**：同向量回放的**单次内** MAD（① 125–174，② 极小，送批 ≈16）。跨次
噪声底**尚未实测**——需要同一份代码 `--repeat 3` 跑一遍。实测后应收紧。

**L4 — 探针基线**（`bench/latency/probe-cosyvoice-feed.mjs`）

`base` 60 次 / `live` 80 次。判据：`>1000 ms` 计数为 **0**，`p90 ≤ 500`。
不进 CI（要 key + 外网）；定位是「换了供应商、或怀疑厂商侧变了时跑一次」。

**做不到自动化的事（不是缺陷，是边界）**

| 想自动化 | 为什么不能 |
|:---|:---|
| 真机绝对 p50 | 台词不同不可比；需要人戴设备 |
| TTS 那 9% 的 1–4 s 长尾 | 需 n ≈ 100+ 才稳定复现，16 轮回放看不到 |
| 真实间隔下的连接冷热 | 回放造不出 5–7 s 的空闲 |
| 误切 C / 答偏 | 没有 ground truth（见 §1.3） |

**L3 的定位是「逻辑回归闸门」，不是「性能验收」。** 性能验收仍然只有真机录音。

### 5.3 固定测试资产

- **标准台词集**：含短停 / 中停 / 长停三种停顿、认领触发句（6 字以上）、
  以及会被切开的开头语（「你说」「你觉得」「我想问你」）。
- **合成停顿样本**：从现有录音切出前后半句，中间插 300/500/700/900/1200 ms
  底噪 —— 人为停顿很难每次都停在 0.5–0.8 s 这一段。
- **三个探针**：`bench/latency/probe-cosyvoice-feed.mjs`（合成首包与分批）、
  `scripts/probe-tts-latency.mts`（连接冷热）、`scripts/partial-timeline.py`
  （ASR 出字节奏）。
- **回放向量**：`20261119-160921`（24 轮，含认领轮与 TTS 长尾）。
  基线在 `bench/replay/baseline/`，文件名只用时间戳，**不含设备地址**。

| 投机认领「完全一致」 | 正确性 | 收紧后答偏归零 | 代码 |
| 判停等待预算 | ② | 缩到 200 后 ② max 从 573 降到 284 | `TURN_JUDGE_WAIT_BUDGET_MS`、`TURN_JUDGE_EXTEND_MS` |

| TTS 预开 task | ③ 建立段 | `setup_ms` 常规 54–77（冷连接 307–578） | `COSYVOICE_PREWARM` |
| 首包静音裁剪 | 下行 | 开头无效静音 146 → 11 ms | 代码 |

### 6.2 已否决（附「什么条件下重新考虑」）

| 否决项 | 理由 | 重新考虑的条件 |
|:---|:---|:---|
| 重训判停模型 | 瓶颈在策略不在模型（重复询问/宽限/预算可绕过） | 策略侧再无可动项，且数据量够 |
| 换现成判停模型 | 公开基准上 AUC 0.754，比「纯静音死等」省 182 ms，但跨模型排名未核实 | 有同口径的对比数据 |
| 语气词放行 | 手写词表 = 弱预测（见原则 2）；「我吃饭」/「我吃饭了」意思不同 | 从真实数据学出判据，且**不花钱**（并行位置） |
| 降封段门槛（不动上行包） | 收益与风险不成比例：门槛 60 只省 20 ms，句内封段多 3 次 | 先改小上行包（25 ms），那时门槛可以维持现状还更快 |
| 覆盖 ≥60% 认领 | 省的时间远小于答偏一次的代价 | 不重新考虑（原则 5） |
| TTS 预合成 | 数据不支持：等待期间合成的收益取决于命中率，而命中率不够 | 判停等待重新变长（即模型变慢） |
| 首批攒 2 字 | 只送 1 字时服务端不开始合成（等 2 s → 首包 2328）；2 字与 1 字同量级 | 服务端行为变化，需重跑 `base`/`live` 两组 |
| 事件循环延迟新仪表 | `loop_max_ms` 已经在 `turn.end` 里常开（全场 ≤7 ms） | — |

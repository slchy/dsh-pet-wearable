## 一、目标和口径

### 1.1 五个用户能感知的量

| 指标 | 定义 | 怎么算 |
|:---|:---|:---|
| **首声延迟** | 停嘴 → 设备收到首块音频 | ①停嘴→定稿 + ②定稿→开轮 + ③开轮→首块。**按逐轮合计排序取 p50/p90**，快车道与委派分开；委派轮再分「到回执」和「到答案」 |
| **慢轮次占比** | 首声 > 1500 ms 的轮次比例 | 同上，数比例。**这是「稳」的指标，比 p90 更不容易被单点污染** |
| **可感知误切** | 用户没说完而系统已经出声 | 三类分开：A 出声前被吸收（合并成一轮）、B 出声后被打断、C 半句被当整句回答 |
| **答偏** | 因文本不完整而答错 | 见 1.3 —— **目前只能人工抽样**，不要假装有自动指标 |
| **多余轮次** | 不是用户完整意图触发的轮次 | 误识别（`Yeah.` / `Thank you.`）、被切开的半句 |

### 1.2 四条口径规则（写死，不许各写各的）

1. **三段相加必须等于合计。** 逐轮算 `①+②+③` 再取中位，**不是各段中位相加**。
   这两者的差别在两头分布时能到 140 ms。
2. **缺数据记 `null`，不拿 0 冒充。** 仪表没落、配对失败、`①<0`（`gate.close`
   配到了上一段语音）都记 `null` 并从该指标的分母里剔除，**不是当 0 算进去**。
3. **坏样本自动剔除，不靠人眼。** 上面那条 `①<0` 已经是脚本行为；同类的
   「`①` 大于整轮」也要能自动识别，不要让分析者每次手工排除。
4. **脚本和线上用同一套判定规则。** 分析脚本里的「命中 / 合并 / 打断」必须与
   `dialog-fsm` 的判断同源；不一致时以代码为准，改脚本。

### 1.3 现在测不出来的两项（要承认）

| 指标 | 可自动测 | 说明 |
|:---|:---:|:---|
| 首声延迟、慢轮占比 | ✅ | 档案三段 |
| 误切 A（出声前被吸收） | ✅ | 前后半句合成一轮、前半句无下行音频 |
| 误切 B（出声后被打断） | ✅ | `turn.end.interrupted` |
| **误切 C（半句被当整句答）** | ❌ | 需要「用户本来还想说什么」这个 ground truth |
| **答偏** | ❌ | 需要标准答案 |

后两项只有两条路：**人工抽样标注**，或用弱代理（「下一轮定稿是上一轮的后缀」
—— 实测 8 个停顿句里 6 个是这种形态，代理勉强可用）。**任何报告里这两项为空，
是在等标注，不是在说「0 次」**。

## 二、原则（六条，每条附来由）

1. **出声之前一切可撤销，只有放出声音才是决定。**
   来由：链路延迟本身就是保护窗口 —— 停嘴后 850 ms 内接上仍落在出声前，
   会合并。所以「等一会儿」不全是浪费，但**要算清等的是保护还是空转**。

2. **刹车用可观测的事实，不用弱预测。**
   来由：`looksUnfinished()` 那张词表、语气词放行表，都是弱预测。删掉之后
   判停的误判率没有变差。弱预测只能放在**不花钱的位置**（与别的环节并行），
   或者**带上限**。

3. **所有等待受同一个上限约束，任何路径不得绕过。**
   来由：`TURN_JUDGE_MAX_OPEN_SILENCE_MS` 就是为这个加的 —— 加之前有分支能
   绕过它一直等。

4. **等待只有被别的串行环节遮住时才免费。**
   来由：判停的 400 ms 原本藏在模型段（300–570 ms）后面；模型段回到 184 ms
   之后，这 400 ms 变成纯成本。**同一条配置的代价会随上游变快而变化** ——
   数字要跟着被遮住的那个环节一起重算。

5. **投机不能改变正确性。**
   来由：投机认领从「覆盖 ≥60%」收紧成「**去全部标点后完全一致**」。宽松的
   判据省的那点时间，远小于答偏一次的代价。

6. **同步上下文和回答用户是两件事。**
   来由：`FAST_LANE_KEEP_TURNS` 曾经让「攒满 4 轮就整句交给 dsh」，于是每 4 轮
   就有 1 轮（用户只是想聊两句）要等 6–8 秒。dsh 需要看到对话 ≠ 用户需要等 dsh。

> 新策略先对照这六条。违反了要写清理由，**而不是不写**。

## 四、改动流程：五个问题

动手前在提交信息或 PR 里回答完：

| 问题 | 不合格的答法 |
|:---|:---|
| **动的是哪个指标、哪一批轮次？** | 「让延迟更低」 |
| **预期收益多少？算式写出来。** | 「应该能省几十毫秒」 |
| **会不会影响正确性？** | 空着不写（等于没说） |
| **怎么验证？探针 / 回放 / 真机，为什么选它？** | 「跑一场看看」 |
| **怎么回退？旋钮是什么？** | 「改回来就行」（没说改哪个） |

两条纪律：

- **一场验收只验一个改动。** 攒在一起就分不清是谁的功劳。
- **新机制先讨论再做。** 自动化 / 自愈 / 监控尤其 —— 代码越多维护量越大。

## 五、测量方法：把踩过的坑写成检查项

这一节是这份文档里最实用的部分。**这几天大部分弯路都出在这里，不是出在代码里。**

| 检查项 | 踩过的具体形态 |
|:---|:---|
| **选择偏差** | 只看「等到放行」的 5 个长等待轮次，得出「0 次用户接着说」——而用户如果在等待期间说话了，那次等待就不会以放行结束，根本不会出现在这 5 轮里 |
| **中位数** | 各段中位相加 ≠ 合计的中位（差 140 ms）。②是两头分布（七成近 0、三成 ~474），中位 8 ms 会掩盖平均值 130 ms |
| **归因** | 只影响少数轮次的改动，要先说明它们**是否跨过了中位**，再谈对 p50 的作用。4 轮从中位之上移到之下让 p50 跳了 127 ms，换个分布更平滑的样本只值几十毫秒 |
| **样本量** | 写明 n 和**能分辨的最小差别**。小于它不下结论。8 轮里投机最多覆盖两三轮到不了中位 |
| **回放 ≠ 真机** | 已确认的三处差异：包节奏（回放 20 ms、真机 75 ms）、轮次间隔（回放常是热的，真机 5–7 s）、连接冷热。**回放能证明「走哪条腿」，不能证明绝对延迟** |
| **基准对应线上的哪个工作点** | 引用任何探针数字前先写清它对应线上哪一版配置。`base` 探针 316 ms 对应「整句一次送完」，而线上是「首 1 字 + 50 ms」= 380 |
| **观测优于猜** | 优先取可复算的证据（`uplink.pcm` 可重算任意增益、`loop_max_ms` 可判主线程卡顿），不针对着代码猜 |
| **改动前后要能对比** | 所以仪表缺了记 `null`，不拿 0 冒充 |

### 5.1 每种验证手段能证明什么

| 手段 | 能证明 | 不能证明 |
|:---|:---|:---|
| **探针**（`bench/latency/`） | 单个外部依赖的分布与边界（厂商长尾、门槛、超时） | 我们自己的链路 |
| **真机回放** | 走哪条腿、合并/打断路径、状态轮转 | 绝对延迟（间隔是热的）、需要真机负载才出现的偶发 |
| **真机录音** | 一切 | 单场绝对值不可比（台词不同），只做**前后配对** |
| **离线统计**（`silence-runs.py` / `partial-timeline.py`） | 分布与门槛的敏感性 | 真实因果 |

### 5.2 固定测试资产

- **标准台词集**：含短停 / 中停 / 长停三种停顿、认领触发句（6 字以上）、
  以及会被切开的开头语（「你说」「你觉得」「我想问你」）。
- **合成停顿样本**：从现有录音切出前后半句，中间插 300/500/700/900/1200 ms
  底噪 —— 人为停顿很难每次都停在 0.5–0.8 s 这一段。
- **三个探针**：`bench/latency/probe-cosyvoice-feed.mjs`（合成首包与分批）、
  `scripts/probe-tts-latency.mts`（连接冷热）、`scripts/partial-timeline.py`
  （ASR 出字节奏）。

## 六、三张清单

### 6.1 在用（机制 → 环节 → 证据 → 旋钮）

| 机制 | 环节 | 证据 | 旋钮 |
|:---|:---|:---|:---|
| 连接保活 | ③ 模型段 | 复用 146–296 vs 新建 375–434；探针空闲 5/8/15/30/45 s 全复用 | `MIAI_HTTP_KEEPALIVE_MS` |
| 判停前起跑（prefetch） | ② → ③ 重叠 | 判停等待基本全被模型段遮住 | `FAST_LANE_PREFETCH` |
| 中间结果投机 | ① 尾巴 → ③ | 认领 3/22（`missing` 全为纯标点） | `FAST_LANE_SPEC_MIN_CHARS`、`FAST_LANE_PARTIAL_SPECULATE` |
| 投机认领「完全一致」 | 正确性 | 收紧后答偏归零 | 代码 |
| 判停等待预算 | ② | 缩到 200 后 ② max 从 573 降到 284 | `TURN_JUDGE_WAIT_BUDGET_MS`、`TURN_JUDGE_EXTEND_MS` |
| 不按轮数强制转交 | 委派率 | 11 轮 overcap → 0 | `FAST_LANE_KEEP_TURNS` |
| TTS 预开 task | ③ 建立段 | `setup_ms` 常规 54–77（冷连接 307–578） | `COSYVOICE_PREWARM` |
| 首包静音裁剪 | 下行 | 开头无效静音 146 → 11 ms | 代码 |

### 6.2 已否决（附「什么条件下重新考虑」）

| 否决项 | 理由 | 重新考虑的条件 |
|:---|:---|:---|
| 重训判停模型 | 瓶颈在策略不在模型（重复询问/宽限/预算可绕过） | 策略侧再无可动项，且数据量够 |
| 换现成判停模型 | 公开基准上 AUC 0.754，比「纯静音死等」省 182 ms，但跨模型排名未核实 | 有同口径的对比数据 |
| 语气词放行 | 手写词表 = 弱预测（见原则 2）；「我吃饭」/「我吃饭了」意思不同 | 从真实数据学出判据，且**不花钱**（并行位置） |
| 降封段门槛（不动上行包） | 收益与风险不成比例：门槛 60 只省 20 ms，句内封段多 3 次 | 先改小上行包（25 ms），那时门槛可以维持现状还更快 |
| 覆盖 ≥60% 认领 | 省的时间远小于答偏一次的代价 | 不重新考虑（原则 5） |
| TTS 预合成 | 数据不支持：等待期间合成的收益取决于命中率，而命中率不够 | 判停等待重新变长（即模型变慢） |
| 首批攒 2 字 | 只送 1 字时服务端不开始合成（等 2 s → 首包 2328）；2 字与 1 字同量级 | 服务端行为变化，需重跑 `base`/`live` 两组 |
| 事件循环延迟新仪表 | `loop_max_ms` 已经在 `turn.end` 里常开（全场 ≤7 ms） | — |

### 6.3 待定（按「影响 × 把握 ÷ 成本」排序）

| 项 | 影响 | 把握 | 成本 | 结论 |
|:---|:---:|:---:|:---:|:---|
| 开头缓存（固定「哥，」单独缓存） | 中（四成轮次每轮早 ~90 ms；移动中位附近轮次，p50 可达几十到一百 ms） | 中（需先试听接缝） | 小 | **先试听** |
| 关「按音频时间计静音」 | 中（封段提前 20–45 ms，每轮受益） | 高（模拟已校准到实测 68 ms） | 中（要改上行包才划算） | 等改上行包一起 |
| 上行包 75 → 25 ms | 中（封段省 25–40 ms，且打断响应更快） | 高（包边界包含关系决定） | 中（改手机 App、线协议） | 由人定 |
| TTS 首包长尾（>900 ms，8/112） | 大（一成轮次等 1–4 秒） | 低（文本已送完、主线程没卡、厂商探针 140 次 0 长尾；只剩「真机 + 认领」这个交叉点未解释） | — | **需一场带 `tts.done` 的真机** |
| 误切 C / 答偏 自动指标 | 中 | 低（缺 ground truth） | 大 | 先做人工抽样 |

## 七、明确不做

| 不做 | 为什么 |
|:---|:---|
| 看板 / 告警 | 一人维护，观测成本 > 收益；`qos.summary` 进档案就够 |
| 自动调参（滑动窗口改预算/路数） | 调参逻辑出问题时排查成本远大于收益 |
| 全局优先级调度器 | 一轮只说一句话，串行就是最优 |
| 新增第六份延迟文档 | 见文末地图 —— 已经有五份了 |

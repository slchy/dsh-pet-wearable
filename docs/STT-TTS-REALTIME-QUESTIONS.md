## 0. 为什么「realtime」不能一句话回答

它对上行和下行是**两个独立的问题**：

```
上行 realtime = STT 边收边出字      （不是等你说完才开始）
下行 realtime = TTS 边生成边播      （不是等整段合成完才开始）
```

任一环节是批量的，端到端就退化为「说完 → 等 → 听」——
跟现在冒烟链路的体验差距不大，选型意义不大。

**目标指标**：从用户说完最后一个字，到眼镜开始出声。

---

## A. STT（上行）

| 问题 | 为什么重要 |
|---|---|
| 是否支持**流式输入**（WebSocket / 双向流 / HTTP chunked） | 不支持就只能等整段，首字延迟 = 说话时长 |
| 是否返回 **partial transcript**（中间结果） | 决定能否「边说边决策」，而不只是边说边显示 |
| VAD 在服务端还是客户端 | 服务端做可省掉手机端静音检测；客户端做则要自己定阈值 |
| 「说完」的判定：显式 end 信号 / 静音超时 / 两者 | 直接决定交互层状态机怎么写（`ADR-004`） |
| 单连接最长时长 / 单次音频上限 | 常驻时要不要周期性重连 |
| 是否支持中途取消 | 用户改主意时的响应速度 |
| 是否要求封装格式（WAV 头 / 裸 PCM / Opus） | 当前上行是 mSBC 解码出的裸 PCM16 16 kHz mono |
| 支持的语言 / 方言 / 中英混说 | 决定是否要额外的语言检测 |

---

## B. TTS（下行）

| 问题 | 为什么重要 |
|---|---|
| **首字节延迟（TTFB）** | 这是用户感知「反应快不快」的唯一指标 |
| 是否支持**流式输出**（chunked / 双向流） | 不支持就只能整段合成后播 |
| 输出格式（PCM16 / MP3 / Opus / 采样率 / 声道） | 当前下行是 AudioTrack 直推 PCM16 16 kHz mono |
| 能否增量喂文本（按句 / 按字） | 决定能不能「LLM 吐一句就播一句」 |
| 是否支持中途停止 | 打断（barge-in）必需 |
| 音色可选范围 / 是否支持克隆 | 影响体验但不阻塞接入 |
| 是否返回精确的音频时长/时间戳 | 用于对齐字幕与打断点 |

---

## C. 共同

| 问题 | 为什么重要 |
|---|---|
| 协议与**认证续期**（token 有效期 / 预签名 / 长连接鉴权） | 常驻长连接必须能续期，不能每 N 分钟断一次 |
| 并发连接数上限 | 单设备场景够用即可，但要确认不是 1 |
| 计费单位（时长 / 字符 / 连接数 / 请求数） | 常驻长连接是否划算 |
| 部署区域与 RTT | 跨区域 RTT 直接吃掉首字延迟预算 |
| 限流与错误码语义（可重试 / 不可重试） | 决定重试策略 |
| SLA / 可用性 | 是否接受单供应商 |

## D. 备选方向（若 MiMo 不满足）

需要**同一份清单**，否则无法比较。

- 各家云厂商的流式 ASR / TTS
- 端侧方案（手机本地推理：延迟最低，质量受限，但省流量与隐私更好）
- 端到端 S2S（音频进 → 音频出）：注意 `ADR-003` 已定 agent 为 CLI，
  S2S 只有在 agent 也能吃音频时才适用，否则要重估 ADR-003

---

## E. 验收

调研结论必须能回答：

> **「从用户说完最后一个字，到眼镜开始出声，能压到多少毫秒？」**

并且**拆解成可归因的几段**：

```
VAD 判停  +  STT 尾包  +  agent 首 token  +  TTS 首字节  +  下行传输  +  播放起播
```

拆不出来，说明调研还不够细 —— 到时候优化只能靠猜。
